# Concepts

## The context problem

An agent starts a session with a fixed context budget. In a repository with dozens or
hundreds of tickets, reading the backlog to find one executable item can consume most of
that budget before any code is written. A human-maintained summary solves the reading
cost but introduces a second source of truth: the moment someone closes a ticket and
forgets the summary, the summary lies.

Ticket Index separates the two things a ticket system contains:

- **Facts** that change mechanically: status, type, priority, owner, dependencies,
  hierarchy, counts.
- **Judgements** that need a person: which domain a ticket belongs to, and what it
  delivers in one line.

Facts stay in ticket frontmatter and are projected by a script. Judgements live in a
small configuration file. The generated index is a deterministic function of the two.

## Three levels

```text
docs/tickets/INDEX.md          overview: how to read, counts, owners, modules,
                               frontier, blocked, missing owners, cross-module edges
docs/tickets/modules/<id>.md   one page per module: stats, ticket tree, cross-module
                               membership references
.tickets/<id>.md               the ticket: the only full copy of problem and decisions
```

A reader moves down this tree. The overview answers "which module?"; the module page
answers "which ticket?"; the ticket answers "what exactly?". Opening a module page is
optional when the overview already names the ticket.

The index is never authoritative for ticket content. It links to the ticket and stops
there.

## Derived, not curated

The script owns everything mechanical:

- **Status counts**, type counts, active/closed totals.
- **Owners**: an active-ticket table derived from `assignee`.
- **Frontier**: active tickets whose `deps` are all closed. This is the "what can start
  now" list.
- **Blocked**: active tickets with at least one open or missing dependency.
- **Missing owners**: active tickets whose assignee is empty or a placeholder such as
  `team` or `tbd`.
- **Hierarchy**: parent/child nesting, with cross-module parents rendered as roots plus a
  pointer.
- **Relations**: cross-module dependencies and links, deduplicated.

A human writes only:

- `module`: the primary domain, plus optional secondary domains.
- `summary`: one line that adds information beyond the title.

This split is why the index cannot drift. There is no field a human can forget to
synchronise, because no mechanical field is stored in the generated output.

## Determinism as a feature

`render` always writes the same bytes for the same inputs:

- tickets are sorted by id;
- modules keep configuration order;
- relations are sorted and symmetric links appear once;
- no timestamps, absolute paths, or environment-dependent ordering reach the output.

That property turns the script into a review tool:

- `diff` prints the unified diff a render would produce and writes nothing. Review only
  those hunks.
- `check` compares every managed file with the expected bytes and fails on stale or
  hand-edited output.
- `render` writes only files whose content changed and deletes generated module files
  whose module no longer exists.

Generated files carry a `<!-- generated by ticket-index; do not edit -->` marker. The
marker is what lets `render` safely remove obsolete module pages without touching
hand-written files that happen to sit in the same directory.

## Module ownership

A module is the **domain where the ticket's conclusion lands**. It is not the person who
raised the ticket, the phase of discussion, or the ticket type.

- A ticket has exactly one primary module, which is where its row is expanded.
- Secondary modules list it under "cross-module membership" and link back. The ticket is
  never duplicated, because two rows could carry two different summaries.
- When a child ticket's parent lives in another module, the child is a root in its own
  module and carries a parent pointer. The tree follows the domain boundary, not the
  reporting line.
- Cross-module dependencies and links are summarised once in the overview. Ticket rows
  only show dependencies that still block.

New domains get a new module; stretching an existing module to avoid adding one makes
the overview less useful, not more.

## Maps and decision tickets

Some work is too large for one session and still too foggy to split into delivery
tickets. The `wayfinder` skill represents that work as a **decision map**: a ticket with
the `map` tag whose children are questions, not implementation slices.

Ticket Index gives maps first-class treatment without special-casing them:

- A map sorts before other tickets in its module.
- Maps are counted per module and in the overview.
- Child tickets follow ordinary `parent` hierarchy and ordinary `deps` blocking.
- Resolved children are ordinary `closed` tickets with their answers in the body.

There is no second index or separate database. A map is just a ticket whose children
happen to be decisions.

## The workflow around the index

The index solves navigation. The companion skills solve what comes before and after:

- `grilling` and `wayfinder` decide what the work is.
- `to-spec` records the decision as a spec.
- `to-tickets` cuts the spec into vertical slices with blocking edges.
- `implement` / `implement-spec` work the frontier, one ticket per fresh context.
- `code-review` checks the diff against repo standards and the originating spec.
- `pr` writes the merge request body.

Each skill reads the same ticket files. No skill keeps a private backlog.
